01 · Overview

Cybersecurity AI without enterprise hardware

Cybersecurity assistants are often built on models that need enterprise GPUs, large VRAM budgets, and always-on connectivity. That excludes independent researchers, students, small security teams, and air-gapped environments.

CyberLite asks a narrow, testable question: can a sub-billion-parameter model be post-trained into a useful cybersecurity assistant while remaining practical to train and run on ordinary hardware?

The project prioritizes low training cost, low VRAM, fast local inference, offline operation, reproducible evaluation, and honest reporting. The target model is Qwen3.5-0.8B; larger models are supported only as experimental controls.

Cybersecurity AI should be accessible without enterprise-grade hardware.

Consumer hardware

Training paths are designed around 4–16 GB VRAM classes, with a CPU-first baseline so the limits are measured rather than assumed.

Offline by default

No paid APIs, no automatic dataset downloads, and no execution of generated commands. Local data stays local.

Evidence first

Every published number must trace back to raw predictions, configuration, dataset version, hardware, and seeds. Until then, it stays blank.

02 · Approach

A reproducible pipeline, from licensed data to local deployment

The default workflow uses no paid APIs, downloads no datasets automatically, and never executes generated commands.

  1. 01

    Licensed sources

    ATT&CK, CWE, NVD, OWASP, Linux and networking documentation, plus project-authored defensive workflows.

  2. 02

    Clean & screen

    Secret redaction, exact and SimHash deduplication, deterministic splits, and a 13-gram contamination screen.

  3. 03

    Post-train

    LoRA and 4-bit QLoRA supervised fine-tuning on Qwen3.5-0.8B; optional offline distillation from a local teacher.

  4. 04

    Retrieve

    A dependency-free BM25 baseline with citation-bearing evidence that is always treated as untrusted data.

  5. 05

    Deploy

    CPU, GPU, and MPS inference, an OpenAI-compatible API, FIM/prefix autocomplete, and a GGUF export path.

  6. 06

    Evaluate

    Fixed seeds, bootstrap intervals, and logged memory and latency. Nothing is promoted to results without review.

04 · Research design

Hypotheses stated before the experiments

Thresholds are project-specific design choices, not universal standards. A hypothesis is falsified if the pre-specified comparison fails; null and negative results will be reported.

Pre-registered hypotheses and operational tests.

Scroll horizontally →

IDHypothesisFalsification criterion
H1 QLoRA adaptation improves held-out cybersecurity MCQ accuracy over the unadapted base model by at least 5 percentage points at matched prompting. Observed improvement < 5 points, or confidence interval includes zero.
H2 At a fixed data and step budget, 4-bit QLoRA retains at least 90% of the held-out accuracy of bf16 LoRA while reducing peak training VRAM. Accuracy retention < 90% or no measurable VRAM reduction.
H3 Offline distillation from a larger local teacher improves held-out task performance over supervised training on the same prompts at equal student compute. No improvement, or a degradation larger than the pre-specified non-inferiority margin.
H4 Retrieval augmentation reduces the lexical unsupported-token proxy on evidence-grounded questions relative to closed-book generation, without a significant drop in answer token F1. No reduction, or token F1 drops beyond the pre-specified margin.
H5 FIM or prefix autocomplete produces usable completions (syntax-valid and above a task-specific similarity threshold) at interactive latency on at least one consumer profile. Threshold not met on any target profile.
H6 Narrow cybersecurity SFT causes a general-capability retention drop of no more than 3 percentage points on the selected retention set. Drop > 3 points with a confidence interval excluding the threshold.

Non-goals

  • Autonomous exploitation or command execution
  • Unlicensed benchmark redistribution
  • Production-readiness claims from smoke tests
  • Leaderboard scores without raw predictions

08 · Autocomplete

Context-aware completion for security work

A local completion service for code, shell commands, detection rules, and configuration. It returns text as data. It does not execute, evaluate, or write generated commands to disk.

Supported profiles

  • bash
  • python
  • powershell
  • yara
  • sigma
  • regex
  • bpf
  • tcpdump
  • nginx
  • dockerfile
  • sql
  • json
  • generic

Two completion modes

  • FIM Fill-in-the-middle prompting, used only when the checkpoint genuinely supports it. Token presence alone is not treated as evidence of FIM quality.
  • Prefix An instruction/chat prompt with before- and after-cursor context. The fallback for instruction-tuned models.
  • Auto FIM if the tokenizer defines FIM tokens, otherwise prefix. The response always reports which mode was used.

● Every response includes executed: false and requires_review: true. Generated commands are never run by the project.

POST /v1/autocomplete 
$ curl http://127.0.0.1:8765/v1/autocomplete \
  -H 'Content-Type: application/json' \
  -d '{
    "prefix": "grep -R \"failed password\" ",
    "language": "bash",
    "mode": "auto",
    "max_tokens": 96
  }'

Returns completion text, mode, latency, token counts, and memory metadata. Bind to loopback unless you add authentication and network controls.

09 · Hardware

Targets, not promises

The 4, 6, 8, 12, and 16 GB VRAM classes are experimental targets. Whether a configuration fits depends on the attention kernel, allocator, sequence length, batch size, optimizer, framework version, and concurrent display use. Always measure.

The planned hardware path

Train and test as much of the pipeline as possible on CPU first, and publish what the CPU path can and cannot do. That baseline establishes which steps are reproducible without a GPU, how long they take, and where the bottlenecks actually are.

Once the CPU evidence is in place, the next step is to seek funding for a CUDA GPU so post-training can continue at research scale. Until that happens, any GPU results in this repository should be read as planned, not measured.

Rule of thumb

A 0.853B-parameter model needs about 1.6 GiB for 16-bit weights, or about 0.4 GiB at 4-bit. Activations, optimizer state, CUDA context, fragmentation, and framework overhead dominate the difference between “fits in theory” and “fits in practice.”

10 · Safety & limitations

Boundaries in the code, and limits that remain

Safety boundaries

  • No generated command or code is executed by the inference, autocomplete, evaluation, or server modules.
  • Autocomplete responses are flagged executed: false and requires_review: true.
  • Evaluation checks Python syntax with ast.parse; it never imports or runs generated code.
  • The local API has no tool-calling or shell tool surface.
  • RAG evidence is labeled untrusted; the prompt tells the model not to follow instructions embedded in retrieved text.
  • Human review is mandatory for any security decision.

These are code-level boundaries, not a complete security architecture. See docs/safety.md ↗.

Known limitations

  • 0.8B parameters impose a hard capacity limit on broad security knowledge, multi-step reasoning, and long-context analysis.
  • Qwen3.5 is a hybrid linear/full-attention multimodal architecture; architecture support can change between library versions.
  • The base checkpoint’s FIM training status is unknown. Token presence is not evidence of FIM quality.
  • Knowledge is frozen at the checkpoint’s training cutoff. Security facts, versions, and mitigations change.
  • The lexical contamination screen catches verbatim overlap only; paraphrased leakage and memorization may remain.
  • Single-machine latency and memory numbers are not portable.
  • There is no sandbox for generated commands, and there is no trained research checkpoint to evaluate.

See docs/limitations.md ↗.

11 · Paper & citation

A living research scaffold

CyberLite: Resource-Efficient Post-Training of Sub-Billion-Parameter Language Models for Cybersecurity and Context-Aware Autocompletion

Modern cybersecurity language models often assume enterprise GPUs, substantial VRAM, and continuous connectivity. CyberLite is an open research program that asks whether a sub-billion-parameter model can be post-trained into a useful cybersecurity assistant while remaining practical to train and deploy on consumer hardware.

The manuscript specifies hypotheses, data methodology, training protocols, evaluation metrics, and ablation plans, and reports verified engineering facts about the implementation. It does not report benchmark results. All performance tables are explicitly marked as pending. The contribution at this stage is a reproducible, safety-conscious pipeline and a falsifiable experimental design, not a claim of state-of-the-art capability.
